# SYMBOLS-FEEDBACK: DOMQL v3 Reactive SVG Generation Bug & Optical Illusions

## Issue Encountered
When dynamically generating SVG child elements (like `<path>` or `<svg>`) inside an existing `<svg>` layer based on a state array, DOMQL v3 fails to render the new elements visibly. The "ghost wire" (which is conditionally rendered via `if:`) works fine, but elements generated by mapping state do not appear in the browser paint layer upon state update. Additionally, even initially rendered wires appeared to be "missing".

## Bugs Uncovered & Solved

### 1. The "Overlapping Nodes" Optical Illusion
The primary reason the user believed the initial wires weren't rendering was an optical illusion caused by the default `state.js`. The nodes were spaced sequentially (`x: 120`, `x: 420`, `x: 720`), but they each had a fixed width of `320px`. 
- Node 1 spanned `120 -> 440`.
- Node 2 spanned `420 -> 740`.
Because Node 2 overlapped Node 1 by 20 pixels, the sockets were practically touching backwards. The bezier wire successfully drew a tiny 20px squiggly line perfectly hidden beneath the dark background of the overlapping node! The wires were drawing, but they were visually occluded.

### 2. SVG Namespace Dropping in Array Mapping (The Real Bug)
Regardless of the optical illusion, there was a critical framework flaw: dynamically appended array items (mapped via `childrenAs: 'state'`) inside an `<svg>` tag occasionally lose their `http://www.w3.org/2000/svg` namespace inheritance during DOMQL's array reconciliation phase. They are instantiated as standard HTML elements `<g>` or `<path>`, which the browser refuses to paint.

## Wrong Solutions Tried
1. **Array Mapping (`childrenAs: 'state'`)**: Mapping the proxy array to include a reactivity tickle. Fails because replacing the array destroys component identity or loses the SVG namespace during re-creation.
2. **`.parse()` Unwrapping**: Calling `connections.parse()` converts the proxy to a raw JS array. This completely broke reconciliation because DOMQL sees new object references on every render, causing it to destroy and recreate the SVGs.
3. **Explicit `key` injection**: Adding `key: (el, s) => s.id` to the child component. Does not solve the issue when the parent array is replaced or mutated because DOMQL array-mapper strips the object keys.
4. **Direct Proxy Mutation**: Mutating the array (`proxy.push(newConn)`) and calling `update({ forceRender: Date.now() })`. The new item doesn't render if the child mapping function isn't forced to track the `forceRender` state.

## The Right Solution
To fix dynamic rendering of SVGs, **COMPLETELY BYPASS** the `childrenAs: 'state'` array mapper. 
Instead, construct a dictionary of explicitly extended components inside the `children` function, ensuring each dynamic key is PascalCase:

```javascript
children: (el, s) => {
  const root = s.root || s
  const _tickle = root.forceRender // 1. Force reactivity!
  const connections = root.connections || []
  const obj = {}
  
  connections.forEach(c => {
    // 2. Generate a valid PascalCase component key
    const safeKey = 'Wire' + c.id.replace(/[^a-zA-Z0-9]/g, '')
    
    // 3. Explicitly construct the child as a first-class named component
    obj[safeKey] = {
      extends: 'WirePath',
      state: c // Manually bind the specific connection state
    }
  })
  
  return obj
}
```
Because `children` now returns a static map of strictly extended components, DOMQL processes each wire exactly like a statically declared child, flawlessly preserving the SVG namespace during dynamic insertions.
